# Case study: Behavior Tracker

## 1. Choose and frame the problem

SEN (special educational needs) teaching teams currently track student behavior using paper ABC (Antecedent-Behavior-Consequence) charts — one sheet per student, kept in a single classroom. This makes data hard to access across locations, hard to aggregate across multiple observers, and slow to turn into action. The only purpose-built digital alternative is not available in the Hong Kong App Store, and generic tools (spreadsheets, forms) lack the structure needed for reliable analysis.

This was worth exploring because it is a real, underserved workflow gap with a well-defined data shape (the ABC chart is a standard, structured framework), a clear user group (SEN teaching teams), and a downstream payoff — faster pattern recognition means faster, better-targeted support for students who need it. It is also a good test case for AI-assisted design: sensitive-data handling, multi-stakeholder access decisions, and AI insight generation all needed to be reasoned through up front — so that the build itself could move fast without revisiting those decisions along the way.

## 2. Design the solution

I used Claude throughout this project — first as a design partner across the full lifecycle of a `DESIGN.md` document, later as an implementation collaborator working from a spec, alongside OpenCode (see Section 3).

The workflow looked like:

- **Draft, then pressure-test.** For each section, I wrote or directed a first draft, and Claude checked it against the rest of the document for internal consistency. For example, it flagged when my summary said "SEN teachers" but my goals implied a broader staff group ("SEN teaching team").
- **Name trade-offs I had not stated.** When I made a scope decision (e.g. team-wide access instead of per-student assignment), Claude helped me separate two things: "why this is fine for now" ("Alternatives") and "what this costs us and when to revisit it" ("Trade-offs"). These became two distinct sections doing different jobs, rather than one section trying to do both.
- **Catch drift across edits.** As the document grew, Claude tracked cross-references — for example, when "API server" was renamed to "API routes" after a tech-stack decision, it flagged the stale terminology left behind elsewhere in the document. This kind of drift is easy to miss by hand across a long document.
- **Question the substance, not just the structure.** When I added AI-generated insights as a feature, Claude flagged that this introduced a different risk profile than the original rule-based design implied — probabilistic output, third-party data handling. It then helped me work through what data gets sent to an LLM provider and how to de-identify it beforehand.
- **Carry decisions into the codebase.** Once the design was set, I had Claude help generate an `AGENTS.md` file that captures the same constraints — no real student data in fixtures, MVP-only AI provider, de-identification requirement — as instructions for any AI coding agent working on the codebase later. The design decisions do not just live in a document, they follow the code.

## 3. Prove it

Two artifacts came out of this process. The first is the design process itself and its output: a complete `DESIGN.md` covering the full lifecycle of the decision — problem framing, architecture, testing strategy, trade-offs, and a pilot readiness checklist. Alongside it is a companion `AGENTS.md` that operationalizes the design's constraints for AI coding agents, and a `README.md` for project orientation.

The second is a working prototype built from that design: a Next.js (App Router) app with Supabase for auth and the Postgres database, with pages for logging and viewing ABC entries, student management, and an insights view. It is backed by database migrations and a Gemini-powered insights endpoint that implements the de-identification and threshold logic specified in `DESIGN.md`. It includes a Vitest unit test suite, covering the logic most costly to get wrong silently — entry validation, threshold gating, de-identification before LLM calls. It also includes a Playwright E2E suite covering the core staff workflow end to end. All development and test data is synthetic, per the design's data-seeding decision — no real student records exist anywhere in the codebase or its fixtures.

Going from design to code, AI's role shifted. In the design phase, Claude acted as a thinking partner, pressure-testing decisions. In the build phase, OpenCode acted more like an implementer, translating `DESIGN.md` into Supabase migrations, the insights API route, and component structure. `AGENTS.md` was written to carry the design's constraints into this phase, and OpenCode was given the file as its operating instructions. The intent was that OpenCode would not silently drift from decisions made earlier — e.g. quietly passing full student records to the LLM "for convenience," or hardcoding the insights threshold instead of leaving it configurable. In practice, `AGENTS.md` prevented the most serious violations but did not catch everything (see Section 4).

As implementation progressed, the architecture itself evolved. Entry writes moved from going through a custom API route to writing directly from the browser to Supabase, protected by row-level security. This simplified the backend to a single API route scoped to insight generation. Each of these changes was reflected back into `DESIGN.md` rather than left undocumented in code alone, keeping the design and the build honest with each other as both moved.

## 4. Analyze the impact

**Before AI (a solo, manual design process):** Writing a design doc this thorough would mean holding every earlier decision in memory while making each new one. In practice, this project showed exactly how that fails. For example, the architecture changed mid-build when entries moved from a custom API route to writing directly to Supabase. That change left the admin-role and deletion decisions inconsistent across three separate sections of the design doc. A promise in "Non-goals" that admins would "handle it manually" contradicted a later note deferring the admin role entirely to v2. That kind of contradiction across sections written on different days would likely have gone unnoticed until a real deletion request came in and no one could act on it.

**What improved:**

- **Consistency at scale, including after the design changed.** The design doc went through many rounds of edits, including a significant architecture revision partway through implementation. Claude re-checked cross-references each time something changed — catching, for example, the admin-role contradiction above, and later flagging that the architecture diagram itself had gone stale once entries stopped routing through an API layer.
- **Speed of structured thinking.** Moving from a rough goals list to a fully reasoned "Alternatives"/"Trade-offs"/"Open questions" structure happened in one sitting rather than several days of separate drafting sessions.
- **Risk surfacing, before and after code existed.** Real risks were caught at two different stages. During design, this included LLM data identifiability under Hong Kong PDPO (Hong Kong's data-protection law, broadly comparable to GDPR) and the free-tier training-data conflict. During implementation, OpenCode surfaced additional risks during an audit. These were caught before deployment, but would have been silent failures in production. A separate risk — nothing stopping repeated clicks on "generate insights" from driving up LLM costs once off the free tier — is now tracked as an open question.
- **More ambitious than a solo build would have attempted.** Alone, a project this size — full design doc, working prototype, test suites, and an agent-instructions file, all internally consistent — would likely have meant cutting scope somewhere. That could have meant skipping the "Alternatives"/"Trade-offs" reasoning, shipping without a de-identification review, or not building `AGENTS.md` at all. AI made it feasible to do all of it at this level of rigor within the available time — not just faster, but at a scope I would not have attempted solo.
- **Implementation speed and consistency.** OpenCode translated the design spec into a working prototype — 7 database migrations, the full ABC form with checkbox groups, the Gemini integration with de-identification, and test suites (unit + E2E) — in a fraction of the time a solo build would take. Components like `EntriesClient` were reused across pages, and documentation stayed in sync as the architecture evolved.

**Where it broke down:**

- **AI could not make the actual judgment calls.** These included team-wide vs. per-student access, which LLM provider to use, what the insights threshold should be, and how to resolve the admin-role contradiction once it was caught. Claude could lay out the trade-offs and inconsistencies clearly, but resolving them required domain knowledge (how small SEN teaching teams actually work) and product judgment that only I had.
- **AI occasionally introduced content that had not been discussed** — e.g. an environment-separation trade-off. Useful as a prompt, but it required me to catch and either confirm or reject it rather than accept it silently.
- **Wording and formatting consistency required extensive, repeated correction** — sentence length, word choice, list punctuation. This was some of the most iterative back-and-forth in the whole process. AI proposed reasonable defaults, but converging on a consistent voice across a long document took many small explicit corrections rather than happening automatically.
- **AGENTS.md compliance was partial, not total.** Although OpenCode adhered to the high-level constraints regarding data handling and de-identification, the implementation diverged from the design specification. Notably, it utilized a hardcoded threshold instead of the configurable setting defined in `AGENTS.md`, featured incomplete RLS policies in the initial migrations, and contained a logic error in the `regenerate-insights` module that short-circuited the API.
- **Debugging required human direction.** The entry-card stale-data issue took multiple rounds of fixes (force-dynamic, useEffect sync, router.refresh removal, missing UPDATE RLS policy). OpenCode could implement fixes but could not independently diagnose the root cause — it required human triage to identify the RLS policy gap.

**What still required human judgment:** Every actual product and policy decision. This included scope boundaries — for example, deciding what could wait until v2. It also included risk tolerance for a pilot vs. production, and domain expertise about the actual user (SEN teaching teams) that no amount of AI reasoning could substitute for. Implementation decisions also required human judgment — which Supabase client to use (server vs. browser), whether to use `force-dynamic` or other caching strategies, and how to lay out entry cards for mobile. It also included every call on how the design doc itself should read — tone, terminology, what counted as "done."

**What I would need to learn to take this further:** The specific legal requirements of Hong Kong's PDPO as they apply to behavioral data on minors. This is still an open question, and a hard blocker before real student data is used, per the "Pilot readiness checklist." On the implementation side, the prototype already uses Supabase row-level security for entry access. I would need a deeper understanding of RLS policy design specifically to be confident it holds up under a real security review. I would also need to set up CI/CD, since tests currently run locally rather than in a configured pipeline.
